Omarchy Lyrion Music Server (LMS) Plugin

Tier 3 Design Plan — v4.1  ·  marketplace: Hardware category  ·  status: build-ready
v4.1 adds authentication & secure-server support (Basic auth, keyring, cover-art proxy).

Goal. A first-party Omarchy plugin for Lyrion Music Server (LMS / Squeezebox): discover servers on the local network, control any player connected to a server, browse and select music, and manage sync groups including per-player audio delay. Marketplace-listing ready, following the proven openhab-omarchy / omaonedrive plugin architecture.

1. Architecture

Layered and decoupled. No polling anywhere.

[LMS 9.x] ── jsonrpc.js (commands) ──▶ [lms-bridge] ── NDJSON ──▶ [Quickshell QML]
   players   ◀── CometD push ────────   (Python, stdlib)         Service / BarWidget / Panel
                                         └─ "pick" (fzf) ◀── terminal ── fzf
  • bin/lms-bridge — Python, standard library only. Owns LMS connectivity: discovery, CometD push subscription, JSON-RPC requests, command dispatch. Emits NDJSON state exactly like oh-bridge.
  • QML trio — Service.qml, BarWidget.qml, Panel.qml. Bar shows now-playing + transport; panel provides search/browse, player selector, sync controls, server settings.
  • Terminal picker — lms-bridge pick <query> routes results through fzf for dense keyboard browsing; numbered-list fallback. ~40 lines, no TUI runtime.

2. Transport & real-time model

ConcernChoiceWhy
CommandsHTTP POST /jsonrpc.js (slim.request)Native JSON-RPC 1.0; clean JSON; no socket management
State updatesCometD/Bayeux on /cometdPush, JSON, single long-poll connection — the exact mechanism Material runs on. No polling
Progress barClient-side clock between pushesSame model as Material; event-driven, not polled
Rejected alternativeTCP CLI 9090 subscribeN+1 sockets + text-tagged parsing; retained as fallback

CometD flow: handshake on /meta/handshake → clientId → subscribe to server/player channels → hold one long-poll connection open. The server pushes the moment anything changes (track, transport, volume, sync membership, player count). Exponential-backoff reconnect when the LMS instance restarts.

3. Authentication & security

  • Server security off (default, the common LAN case): no credentials required.
  • Server security on: jsonrpc.js and /cometd use HTTP Basic auth on every request (verified against two independent working implementations: the lms-mcp server and the MadPatrick LMS→Domoticz plugin). The CLI login command is the telnet-only mechanism and is not used here.
  • Credentials stored only in the system keyring (secret-tool, same CredentialManager.qml flow as the openhab-omarchy API token) — never in config or process arguments.
  • Connect flow: unauthenticated serverstatus probe fails → panel flags "auth required" → prompt for username/password → Test button validates; remembered-server list keeps an authRequired flag. Discovery sweep does the same per candidate.
  • Cover art on secured servers: QML's Image element cannot attach an HTTP Authorization header, so the bridge serves /music/<id>/cover through a localhost proxy using its stored credentials.
  • Audio streaming is untouched — player devices pull their own streams from LMS directly, not through the plugin.

Pin in Phase 1 (requires testing against a real password-enabled server): exact failure signal of an unauthenticated request (HTTP 401 vs empty {}), whether the /cometd and cover-art endpoints honor Basic auth, and the proxy scope.

4. Server discovery

  • Scan: HTTP sweep of the local subnet on :9000; validate each hit with serverstatus, name from _name. Auth-required candidates are flagged for credential entry, not dropped.
  • Manual entry: host:port field + "Test" button — the guaranteed path on any network.
  • Persist: remembered-server list; auto-connect to the last used server on start.
  • Phase 2: UDP probe on 3483 if the sweep underperforms.

5. Player control

  • serverstatus / players enumerate players; a dropdown selector (OmaOneDrive account-switcher pattern) targets commands at <playerid>.
  • Per player: play / pause / next / prev, volume slider, seek, power.
  • Sync groups: syncgroups, sync_master / sync_slaves → "synced to Kitchen" badge; join/leave via sync / sync -.
  • Per-player audio delay (multi-room echo fix): write playerpref <id> <token> <ms>, read via players … playerprefs:<token>. Slider appears only when the player is synced. Pref token and value direction are pinned against a live server in Phase 1 (likely syncDelay, bounded ~0–5000 ms, applied on next resync; persists across unsyncs).

6. Browsing & selection

  • Panel search: albums / tracks / artists / playlists …search:<q> with cover art (/music/<id>/cover); play now / add to queue / play on selected player.
  • Hierarchical browse: LMS menu: extended queries (Artists→Albums→Tracks, Genres, Playlists, Radio).
  • fzf picker: lms-bridge pick — the dense keyboard flow the TUI was meant to serve.
  • Now-playing art: /music/current/cover.jpg?player=<id> — served through the bridge proxy on password-protected servers.
  • Phase 2: optional terminal TUI (Go + Bubble Tea) as an "advanced console" — not the centerpiece.

7. Keybindings & installer

  • No interactive install wizard. Omarchy installs are non-interactive (omarchy plugin add); a blocking read -p breaks automation and the marketplace baseline.
  • No keybinding writes in Phase 1. bindings.lua is user-owned territory. Phase 2 adds an opt-in "Add media keys" toggle appending o.bind(XF86AudioPlay|Next|Prev) — idempotent, reversible via hl.unbind.

11. Risks & open items

  • CometD channel names / handshake details pinned against a live LMS during P1.
  • Exact audio-delay pref token confirmed via a playerpref probe at build time.
  • Basic-auth failure signal on a secured server (401 vs empty {}) pinned in P1.
  • /cometd and cover-art endpoints' response to Basic auth verified against a real password-enabled server in P1.
  • Multi-subnet homes → manual entry is the guaranteed fallback.

12. Verification

  • Stub-LMS HTTP responder in tests: verify request framing, CometD event dispatch, NDJSON output.
  • Manual acceptance against a real LAN server: discovery, multi-player control, sync delay, auth.
